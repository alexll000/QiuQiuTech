# UI Governance

最后更新：2026-05-09 11:55 (UTC+8)

## 目标

保持“高级、简约、时尚、专业”的统一视觉，避免首页模块膨胀和风格漂移。

## 视觉规则

1. 主色系以 logo 色值为核心：深蓝 / 青绿 / 暖黄（避免无关高饱和色抢主视觉）。
2. 首页首屏只保留一个主叙事区，不堆叠多个同级 Hero。
3. 内容区优先信息密度，不做营销型大面积空白。
4. 卡片圆角、边框、阴影必须复用现有组件风格，不新增“另一套设计语言”。
5. 动效仅用于强调层：
   - 背景动效可用但需低干扰
   - 不影响文本可读性与交互点击

## 布局规则

1. 首页核心模块上限 6 个（不含页脚）。
2. 模块间距统一，不允许同屏出现明显不等距断层。
3. 列表页采用固定栅格与稳定卡片高度，避免跳动。

## 交互规则

1. 所有关键动作必须有状态反馈：`loading/success/error`。
2. 表单输入校验前置，不把错误延迟到提交后集中爆发。
3. 弹窗登录只在顶部入口触发，不在页面主体重复放置。

## Workbench 规则（新增）

1. 新增或重做基础组件时，优先进入 `web/src/components/ui/*`，不要继续把同类按钮、标签、输入框散落在页面文件里临时实现。
2. 关键公开前台模块改动后，默认要同步补 Storybook story，至少覆盖：
   - 默认态
   - 长文案态
   - 空态或弱数据态
   - 移动端可读性
3. Storybook 里的 token、primitive、pattern 是页面开发上游，不是展示型 demo；一旦页面与 story 漂移，应先修 story 对应基线。

## 公开前台高优先级约束

1. 公开前台的信息架构必须先按用户任务组织，不能先按技术实现组织。
2. 登录、注册、账号找回、扫码等账户流程，必须围绕“我要登录”或“我要注册”展开，不能把当前会话、测试入口、技术状态与主流程并列展示。
3. 禁止在 C 端页面直接展示开发态、测试态、联调态、内部态信息。
   - 包括但不限于：体验账号、会话 ID、mock/fallback 字样、内部 reviewer 占位值、环境说明、实现边界提示。
4. 禁止把开发语境字段名直接暴露给用户。
   - 例如“账号标识”“mock 审核队列”“admin-mock”这类表达，必须改写成用户可理解且业务自然的话术。
5. 允许在实现层保留 fallback、mock、降级与占位逻辑，但这类机制必须隐藏在代码层，不得成为公开界面的文案内容。
6. 已完成状态应弱提示或自动跳转，不得反客为主占据页面主视觉。
   - 例如已登录用户进入登录页时，不应看到大面积状态说明区，而应优先返回用户中心或仅保留轻量提示。

## 验收

每次 UI 改动后至少检查：

- 首页（桌面 + 移动）
- 内容列表页
- 投稿页
- 合作对接页
