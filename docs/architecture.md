# QiuQiuTech Architecture

## 1. 当前阶段定义

QiuQiuTech 当前处于：

**前台框架已成型，后台技术路线已明确，准备从静态演示数据切向真实 CMS / 数据模型 / 审核流的阶段。**

## 2. 总体架构

```text
QiuQiuTech/
├─ docs/                     # 文档与接手资料
├─ web/                      # Next.js 前台
├─ cms/                      # Directus 后台
└─ scripts/                  # 抓取、导入、同步脚本（后续新增）
```

## 3. 分层职责

### `web/`

负责：

- 品牌化前台体验
- 首页策展
- 内容列表与详情
- 专题页
- 合作对接页
- 投稿前台入口
- SEO 输出

不负责：

- 内容审核逻辑
- CMS 数据编辑
- 后台角色权限
- 抓取执行

### `cms/`

负责：

- 内容管理
- 投稿审核
- 合作需求审核
- 标签分类
- 专题管理
- 展示位管理
- 用户管理
- Dashboard 看板

### `scripts/`（后续）

负责：

- 抓取与 URL 导入
- 数据清洗
- 批量同步到 Directus
- 定时任务

## 4. 数据流方向

### 内容流

```text
抓取源 / 运营录入 / 用户投稿
        ↓
     Directus 审核池
        ↓
    审核通过 / 驳回 / 修改
        ↓
      发布到正式内容
        ↓
  首页 / 列表页 / 专题页 / 榜单页
```

### 合作流

```text
用户发布合作需求
        ↓
      Directus 审核
        ↓
      发布到合作广场
        ↓
    用户申请联系 / 平台撮合
        ↓
     状态变更与后续追踪
```

## 5. 为什么现在选 Directus

当前不是在做纯工程练习，而是在做一个：

- 有运营后台需求
- 有内容审核流
- 有专题策展
- 有展示位管理
- 有合作卡审核

的内容平台。

Directus 在当前阶段的优势是：

- 后台 UI 成熟度高
- 配置速度快
- 更适合快速得到可运营后台
- 后续仍能扩展

Payload 不是不行，但在“后台成品感 + 当前效率”这件事上，现阶段 Directus 更合适。

## 6. 下一步架构演进

### 当前

```text
web -> site-data.ts
cms -> 待正式接入
```

### 下一阶段

```text
web -> Directus REST / SDK
cms -> PostgreSQL + Directus
scripts -> 导入 Directus
```

### 再下一阶段

如业务变重，可增加独立业务 API：

```text
web -> API / Directus
api -> 自定义业务逻辑
cms -> 内容与运营后台
scripts -> 抓取与同步
```

## 7. 接手开发优先顺序

1. 起 Directus 本地实例
2. 建核心 collections
3. 建角色权限
4. 建 Dashboard 与审核面板
5. 先接首页和内容页数据
6. 再接合作对接和投稿状态
